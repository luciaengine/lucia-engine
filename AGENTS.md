# AGENTS.md

Entry point for coding agents working in this repository, whichever tool runs them: what this is, how to build, test and land a change, and a map of where the rest lives. Read what the map points at when the task touches it, not everything up front.

## Map

- `CLAUDE.md` for the engineering values, the conventions that invert other engines' habits, the debugging instruments, code style and working discipline; where files disagree, it wins.
- `CONTRIBUTING.md` for the short form of the rules, written for people.
- `.claude/rules/rendering.md` when touching the renderer, shaders or GPU debugging; `ecs.md` for ECS components and systems; `editor-ui.md` for editor UI, CSS, settings pages and asset mounts; `scripting.md` for the managed side; `documentation.md` for `docs/`.
- `CodingStyle.md` for naming and layout; `BUILD.md` for building from a fresh clone on every platform.
- `CONTRIBUTING.md` defines the two-repository boundary: general engine code, documentation, and maintained workflow material stay here; restricted console code and documentation stay in the private console repository. General contributors build, test, and review changes using this repository and its documented dependencies. Keep maintained workflow guidance under `docs/development/` and reusable scripts under `Tools/`; keep generated evidence in pull request attachments or an external evidence folder.

## What this is

A C++20 game engine: Vulkan-first GPU-driven renderer, archetype ECS, CoreCLR (.NET 10) hot-reload scripting, and a CSS/XML-driven editor. Windows is the primary platform (Visual Studio 2026, CMake 3.25+, vcpkg in manifest mode); macOS, Linux and Steam Deck presets exist. `Engine/Modules/` holds every subsystem as its own library, `Apps/Editor/` the editor, `Apps/Player/` the runtime, `Managed/` the C# side, `Tests/` the integration tests, `docs/` user documentation and `docs/development/` maintained engineering guidance.

## Build

```bash
cmake --preset vs2026-x64-local -DBUILD_TESTING=ON                                   # tests are OFF by default
cmake --build --preset vs2026-x64-local --config DebugFast --target <Target> -j 12
```

- **DebugFast** is the daily configuration: asserts live, warnings are errors. **Debug** adds runtime checks and is slow (10 to 30 fps in the editor is expected). **Release** is the only configuration a performance number may come from, on both arms: `/Od` changes which side of a frame is the bottleneck, so a Debug delta can have the wrong sign.
- Presets: `vs2026-x64-local` is the daily driver (no unity build, one edit recompiles one file); the `-unity` variants compile faster cold and slower per edit; `-asan` for memory bugs; `ninja-x64-local`, from a Visual Studio developer shell, is the fastest for incremental iteration in a tree you keep. `-j 12` is one lane's share when several build at once; a lone build on an idle machine may use `-j 24`.
- Optional MCP server: after a clone, and after a `git pull` that touched `mcp/`, run `cmake --build --preset <preset> --target McpServer`. Configure registers this incremental target only when npm is on PATH; configure runs no npm commands.
- Build the targets the change needs, never the whole tree: every target that compiles a touched file, which means the focused suites' targets and `Editor` or `Player` for an application source that no test target compiles, live check or not.
- Build with the CMake commands above and run focused suites as shown below. Reusable build and test wrappers maintained in this repository may be used, but no external workflow checkout is required. Save full logs in an external evidence folder and report the exit code, first unique errors and warnings, fresh binaries, declared = ran + disabled, skips with reasons, and failures. Read a tail, count, line range, or focused search rather than whole logs. The MCP `build_engine` and `get_build_status` tools provide summaries when available.
- Never build in a checkout someone else is working in, and never while an editor runs from that build's output: the build overwrites DLLs the editor has loaded (a long-lived editor session runs from an isolated copy of the staged tree). Use one git worktree per change and keep it until the change merges. A lane checkpoints `STATUS.md` in its evidence folder after every step, so a fresh lane can continue from it. A fresh worktree configures with the shared toolchain path and its own vcpkg root (`-DCMAKE_TOOLCHAIN_FILE=<primary checkout>/dependencies/vcpkg/scripts/buildsystems/vcpkg.cmake -DBUILD_TESTING=ON`, no `VCPKG_INSTALLED_DIR`); ports come from the machine-wide binary cache in about a minute, the engine compiles cold once. A configured tree is never renamed or moved and a build directory is never copied between trees: the cache and project files hold absolute paths.
- Coordinate builds, suites, and editor starts with anyone taking timing measurements on the machine. Use a shared timing-lock tool when the team has configured one; it is not a build dependency. Only measurements reserve an exclusive timing window, and the holder releases it within the agreed cap.
- Runtime files live next to the executable under `build/<preset>/bin/<config>/`, staged by the build (`StageEditorAssets`, `ge_stage_runtime_dependencies`, `StageTestAssets`). Never resolve a runtime path back into the repository, and never use the repository root as a project root: use `Apps/Editor/Player/` or a dedicated test project.

## Test

```bash
./build/<preset>/bin/DebugFast/Tests/<Suite>.exe --gtest_output=xml:<path>          # one process per suite
```

Google Test, one executable per module or responsibility; `ctest --test-dir build/<preset> -C <config> -N` lists everything. Tests run from the staged output with the build directory as working directory.

- Gate a change with its focused suites: the suites that exercise the touched code, using a maintained test map in this repository when available (a test reads or calls it). A suite that merely compiles a touched header is built, not run. Each focused suite runs whole, in one process: no `--gtest_filter` inside it at a gate. A filter is for a red-first run, a mutant and a repeat of one failing test; a filter that matches nothing is void, not a pass.
- The `run_tests` summary or the suite's result XML, and the capture tools' record lines, are the record of a run; `get_log` is called with a level and a pattern, with `since` after the first call (paste the `next` line the reply ends with), never polled and never after a build, a suite or a capture.
- Report declared = ran + disabled and ran = passed + failed + skipped for each whole-suite gate, using the result XML. Name every skip with its file:line reason and report disabled tests separately; a suite that only skips does not verify the behavior. Interrupted or incomplete runs are reported as incomplete, not forced into these totals. The gtest XML, attached to the evidence, is the record of a run, not a count of log lines; keep `[  FAILED  ]` searches out of `&&` chains because a zero-match search can exit 1.
- At each implementation step, review fold, or integration update, run only the checks affected by that delta. Fix failures the change caused and rerun without asking. Comments, documentation, and instruction-only changes require a diff and consistency review, plus relevant format or link checks when applicable; they require no engine build, suite, capture, or timing run. Test-only changes build and run the whole suite that holds the changed test. Build and configuration changes require the affected configure, build, or staging checks. Native code changes build the affected targets in DebugFast with warnings as errors and run their focused suites. Player behavior is checked in Player; editor behavior is checked in the editor. Changes that can alter rendering add focused captures in the affected application, and performance claims add before/after Release measurements. Record the chosen checks and their rationale before running them.
- The full mapped set is not a per-pull-request gate: it runs as the pre-release validation and as one batched run on main each day.
- A behavioural claim ships with a test that is red without the change and green with it; say which run was red. Keep tests to what the task asks for, sized like the neighbouring test files; scratch checks are not committed.
- Before readiness, fetch the verified target base and validate the final combined tree against that exact commit. Integrate it into the feature branch at the final review fold when needed, then run the affected checks above. Inspect both the commits and complete three-dot diff against the fetched base; every changed file and hunk must serve the requested scope. A clean textual merge, non-overlapping filenames, or a limited include search does not establish independence. Reuse earlier build/test evidence only when reliable build dependency records and a review of runtime contracts, implementation changes, assets, schemas, generated code, and configuration establish that the base delta cannot affect the verified behavior. Record both SHAs, the evidence, and which checks were reused. If independence is uncertain, validate the combined tree. Instruction-only and documentation-only changes still use their applicable checks, not an engine rebuild. Recheck the target base before merging; a new affecting delta requires renewed validation.
- Every path handed to a Windows program is a `C:/...` path: `--gtest_output=xml:`, log files, `APPDATA` redirects. Git Bash does not convert a `/c/...` path inside such an argument, so it lands under `C:\c\`, a tree nothing reads; a run that produced one is void until rerun.
- Anything visible ships with recorded-pose screenshots (build SHA and full pose on every capture) from an isolated editor instance on a verified-free port that the lane checks is still its own before every call (a freed port is reused by the next launch), stopped by its recorded process id; never kill an editor you did not launch.
- Protect the owner’s active desktop session. Do not synthesize operating-system input (`SetCursorPos`, `keybd_event`, `SendInput`, `mouse_event`) or capture the desktop. Drive the editor through its debug port and Player through its own flags and log; take captures through render-graph readback. Start the editor with the required view active. On a shared desktop, do not call focus-changing operations such as `focus_view`, tab activation, or `move_window`. If foreground rendering is required, use a validation machine or desktop session explicitly authorized for that purpose and coordinate its ownership before using a documented app focus operation. Authorization to run checks does not by itself authorize taking over the owner’s desktop. If an authorized rendering session is unavailable, report the affected check as not verified; do not treat black or throttled output as a valid result.
- An evidence folder holds evidence: captures, test results, logs, notes. Scratch output (build logs, exit codes, draft pull request bodies) goes there too, never beside the checkouts, into the repository or into a worktree. Never configure a build or copy an editor build into one. Isolated editor copies live in a scratch folder of their own and are deleted when the editor that ran from them stops; the final report lists what is left on disk, with sizes.

## Land

- Before opening the pull request, run the `change-scrutiny` skill over the diff (reuse of the engine's types, utilities, containers, controls and the job system; placement; names; the public surface; the whole coding style read against the diff) and carry its "Reuse and surface" table in the body; a reviewer reads it first.
- A change is ready when its applicable checks from Test pass on the final combined tree, required live evidence is recorded, and no correctness blocker or mandatory requirement remains unresolved. Documentation and instruction changes follow their scoped checks rather than a native build gate. The pull request body states the user’s problem, the resulting behavior, the verification evidence, justified exceptions, and what is not verified. Impersonal phrasing. After opening or updating the pull request, verify its actual target repository/base and complete changed-file diff.
- IMPORTANT: no attribution lines, tool signatures or session links in commit messages or pull request bodies. The repository's commit hook strips trailers by design.
- One purpose per pull request and per commit, and the purpose complete: a pull request is a whole reviewable step of a feature that a user can see or a test can exercise. Include a scoped refactor when it is necessary for that purpose; keep unrelated cleanup separate. An arc whose intermediate steps would leave the default branch with a half-feature lives on a feature branch; its slices receive review at the depth they need, and the final pull request takes the applicable gates. Shader and GPU changes that each need a timing window, and fixes another team waits on, stay small. Before creating a branch, verify the intended target repository and its actual default or explicitly requested base branch, fetch that repository’s current base, and create a separate branch/worktree from that fetched commit for each independent pull request. Do not assume `origin`, a fork, a local default branch, or the current checkout is the intended base. Use a stacked base only with explicit user authorization. Use plain commits after review; never force-push a shared branch.
- A change taken over from a public pull request carries "(contributed by <name>, OpenEngine #N)" in its title; a squash merge's author is the merger, so the title is where the credit lives.
- A pre-existing bug or improvement you notice is reported as a follow-up, not folded into the change, unless the requested behaviour cannot work without it.
- A change that makes authored data newly refused (a pipeline, a scene or a material that loaded yesterday and is rejected today) says so in the pull request body with the one-line fix for the data.
- User-facing text (labels, tooltips, notices, documentation) uses American spelling and never names another engine; import features keep their names.
